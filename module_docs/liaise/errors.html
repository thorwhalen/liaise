liaise.errors

Processor error taxonomy (design §3.6): classify how a run ended, and what the tick does.

A run is classified from its claude stream-JSON output. Structured fields are checked before strings, and the first match wins, so a run that failed authentication and then crashed is auth_expired, whose action (hold the processor, count no dispatch) is the right one. A run whose final result is a success is never classified by strings it happens to contain.

ERROR_ACTIONS is the single source of truth for what each class does to a case; the tick consults it and decides nothing about error classes on its own.

liaise.errors.DFLT_QUOTA_DEFER = datetime.timedelta(seconds=1800)

Fallbacks and caps for deferrals, named rather than inlined.

class liaise.errors.ErrorAction(state: str | None, auto_hold: str | None = None, notify: bool = False, counts: bool = True, defer: timedelta | None = None)[source]

What the tick does with a case whose run ended in one error class.

state is the case’s next state, or None to leave it unchanged; intake makes the case dispatchable again (its session id stays, so the next dispatch resumes). counts is whether the run counts against the daily dispatch cap.

None for any other failure, which the tick reconciles to needs-owner as 0.0.x did.

Read stream-JSON lines: the final result event, the last rate-limit info, retry errors.

Lines that are blank, not JSON, or not objects are skipped: a stream cut off mid-line by a kill must still yield whatever came before it.
